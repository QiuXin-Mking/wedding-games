# wedding-games

婚礼互动答题小游戏 H5 —— 大屏 + 宾客手机实时同步答题。

宾客扫码入场 → 系统分配昵称 → 主持人播报题目 → 大屏与手机同步出题倒计时 →
宾客作答 → 实时计分 → 大屏排行榜。共 13 题。

**线上地址**：`http://119.29.186.63:8888/`

| 端 | 地址 |
|----|------|
| 宾客 | `http://119.29.186.63:8888/` |
| 大屏 | `http://119.29.186.63:8888/screen?key=<口令>` |
| 主持人 | `http://119.29.186.63:8888/host?key=<口令>` |

> **口令绝不写进仓库。** 本仓库是 public，而这两个口令一旦泄漏，
> 任何人都能打开主持人控制台点「跳过本题」「公布最终排名」——
> 足以当场毁掉整场游戏。
>
> 口令只存在于服务器的 systemd 配置里，用这条命令查：
>
> ```bash
> ssh root@119.29.186.63 "grep -E 'SCREEN_KEY|HOST_KEY' /etc/systemd/system/wedding-quiz.service"
> ```
>
> 换口令：改上面那个文件里的两行，然后
> `systemctl daemon-reload && systemctl restart wedding-quiz`。
> 换完当场通知大屏值守和主持人，旧链接会立刻失效。

## 本地跑起来

```bash
npm install          # 只会装一个包：ws
npm start            # 默认 8888 端口，无构建步骤
npm test             # 150 个用例
```

打开 <http://localhost:8888/>。大屏和主持人端的默认口令是 `screen` / `host`。

常用脚本：

```bash
npm run check:nicknames          # 校验昵称池（U1~U5）
npm run qr -- http://<地址>/     # 重新生成入口二维码
npm run names                    # 打印昵称池，供人工过目
npm run loadtest -- --clients 400 --url ws://<地址>   # 并发压测
```

## 双题库切换

两套题库都在仓库里，靠环境变量切，**不改代码、不重新构建**：

| 题库 | 文件 | 何时用 |
|------|------|--------|
| 测试题库 | `questions/test.json` | 开发、联调、彩排（**默认**） |
| 婚礼题库 | `questions/wedding.json` | 正式场 |

```bash
# 切到正式题库
ssh root@119.29.186.63
sed -i 's/QUIZ_BANK=test/QUIZ_BANK=wedding/' /etc/systemd/system/wedding-quiz.service
systemctl daemon-reload && systemctl restart wedding-quiz
```

### ✅ 切完必须确认

**看大屏左上角的角标**：

- 显示「**正式题库**」→ 切对了
- 显示「测试题库」→ **没切成功**，全场会答一套通用常识题

指定 `wedding` 而文件不存在时，**服务端会直接启动失败并报错，绝不会静默回退到测试题库** ——
婚礼当天用错题库是不可接受的事故，这是唯一的防呆。

题库格式见 `questions/test.json`。正题必须恰好 13 道，备用题至少 1 道
（备用题供 `host:back` 换题用，不参与正常出题顺序）。
格式不对时启动会失败并指出是第几条的什么问题。

## 现场操作手册（主持人）

### 开场

1. **喊大家扫码**，然后**准备约 8 秒的垫场话**
   400 人同时扫码需要这么久。宾客 1 秒内就会看到「正在进入」，不会白屏，但要等页面加载完。
   > 可以说：「桌上都有二维码，微信扫一扫，不用打字。扫完会给大家起个名字，
   > 等下上大屏就认这个名字……」

2. 看控制台的「**已作答 N / M**」，M 就是已入场人数，够了就点「**开始游戏**」

### 每道题

1. **先念完题目和四个选项**，再点「**下一题**」
   ⚠️ 点下去倒计时**立刻**开始走。念题不占答题时间，但顺序不能反。
2. 20 秒倒计时期间，控制台会显示已作答人数
3. 结算后控制台给出**唱分四项**：已作答人数、答对人数、正确答案、当前第一名
   > 可以说：「这题 86 个人作答，只有 23 个答对，正确答案是 B！
   > 目前领先的是……」
4. 点「**下一题**」继续

### 救场（收在「救场操作」抽屉里）

| 按钮 | 什么时候用 | 后果 |
|------|-----------|------|
| **延长 10 秒** | 大家还没答完 | 只给看清题的机会，**延长期间提交一律 0 分** |
| **提前结算本题** | 有人挂机不答，不想干等 | 未提交者记未作答，正常结算 |
| **重新公布结果** | 大屏卡住了 | 只重播画面，**不动任何分数** |
| **把二维码打回大屏** | 有人迟到没扫上 | 大屏弹出大二维码 25 秒 |
| **跳过本题**（危险） | 题目有问题 | **全员 0 分且不可撤销**，大屏显示「本题作废」不公布答案 |
| **换一道备用题**（危险） | 念错题、题目有歧义 | 原题作废，换备用题重来。**不能重答原题** —— 答案刚公布过，重答等于集体送分 |

危险操作会二次确认。可撤销的操作不拦你。

### 发奖

在「宾客管理 / 导出」里搜昵称，点「**点名**」——
**那位宾客的手机会全屏亮起「叫的就是您，请举手」并震动**。

随机昵称和真人之间没有联系，光靠念名字容易出事：嘈杂环境里听错，
或者本人不敢举手怕认错。点名是让当事人确信「叫的是我」。

结束后不用做任何导出操作 —— 成绩完整留在服务器的事件日志里，事后随时可还原。

## 故障应急预案

> 每一级都配了**可以直接念出口**的话。慌的时候不要临场编。

### 一级：大屏黑屏

**先知道这件事**：题目在**每个人手机上都有**，游戏可以继续，不必暂停。

> 「大屏这边稍微调整一下，大家看手机就行，我们继续。」

处理：让大屏值守刷新页面，会自动恢复到当前题。
**刷新后记得重新点「全屏」** —— 不全屏的话地址栏里的口令会投给全场。

### 二级：主持人端点不动

**先看控制台右上角**：

- 显示「**本机掉线 · 服务器正常**」→ 是你这台设备的网络问题，
  用备用设备打开同一个 `/host?key=...` 链接接管
- 显示「**服务器不可达**」→ 跳到第四级

> 「稍等一下，我换个设备。」

### 三级：服务挂了（全场同时掉线重连）

服务会在 2 秒内自动拉起，并从日志恢复所有人的分数。**等 10 秒。**

> 「系统打个盹，马上回来，大家的分数一分都不会少。
> 正好趁这个空当，让我们再次把掌声送给今天的新郎新娘——」

恢复后会停在上一题的结算态。由你决定：
- 点「**换一道备用题**」：刚才那题重来
- 点「**下一题**」：那题作废，继续往下

### 四级：服务器整个连不上

**这一级没有技术解法。** 判定标准：**等满 30 秒仍然打不开**。

**处置方式：放弃这个环节，直接进下一个节目。**

> 「看来今天的网络不太配合，这个游戏我们就先放一放。不过分数都在，
> 我们回头再公布——接下来先请大家看……」

**不要临场改成口头抢答。** 没有屏幕、没有计分，三百人一起喊答案只会更乱。
这是新人定下的口径：概率极小，真碰上了不纠结，往下走。

> 因此**不需要**准备纸质题卡作为应急手段，也**不需要**记分员 ——
> 这两样原本都只为「转口头抢答」这条预案服务，该预案已取消。

## 部署

服务已装好并开机自启。

```bash
ssh root@119.29.186.63
systemctl status wedding-quiz      # 状态
journalctl -u wedding-quiz -f      # 实时日志
systemctl restart wedding-quiz     # 重启
```

### 发布新版本

```bash
# 本地
tar czf /tmp/wq.tgz --exclude=node_modules --exclude=.git --exclude=data .
scp /tmp/wq.tgz root@119.29.186.63:/tmp/

# 服务器
S=$(date +%Y%m%d-%H%M%S)
mkdir -p /opt/wedding-quiz/releases/$S
tar xzf /tmp/wq.tgz -C /opt/wedding-quiz/releases/$S
cd /opt/wedding-quiz/releases/$S && npm install --omit=dev
ln -sfn /opt/wedding-quiz/releases/$S /opt/wedding-quiz/current
chown -R wedding:wedding /opt/wedding-quiz
systemctl restart wedding-quiz
```

### 回滚

```bash
ls -t /opt/wedding-quiz/releases          # 找上一个版本
ln -sfn /opt/wedding-quiz/releases/<上一个> /opt/wedding-quiz/current
systemctl restart wedding-quiz
```

**5 秒完成，`data/` 不受影响** —— 事件日志放在 releases 之外，重新部署不会冲掉比赛数据。

### 改完代码后

静态资源走 **ETag 协商缓存**（`cache-control: no-cache`），刷新一下就拿到新版，
**不需要强制刷新**。

> 早先用的是 `max-age=3600`，代价是改完部署后，凡是访问过的设备一小时内
> 继续吃旧版本 —— 测试期真的踩到：修好的页面发上去，手机照样白屏。
> 强缓存在婚礼当天本来也不省带宽（每位宾客只扫一次码，首访无缓存可用）。

## 技术约束

零框架、零构建、纯 JavaScript，**运行时依赖只有 `ws` 一个**。

这不是洁癖：婚礼当天只有一次机会，依赖越多，构建失败、版本冲突、
Node 不兼容的概率越高，而这些问题全会在最不该出问题的时候出现。

附带收益是首屏只有 **7 KB**（gzip 后），400 人集中扫码约 7.6 秒就能全部进场；
若换成 React，首屏 150 KB+，同样人数需要 164 秒。

详见 `docs/01-需求与验收标准.md` 的 C6 依赖预算表。
