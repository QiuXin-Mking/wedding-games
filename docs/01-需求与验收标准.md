# 01 · 需求与验收标准

> 婚礼互动答题小游戏 H5 ｜ 婚礼日期 2026-10-06
> 本文件自包含：**只写最终结论与可检验的标准**，不含推导过程。

---

## 1. 产品定义

婚礼现场「大屏 + 宾客手机」实时答题：宾客扫码入场 → 系统分配昵称 → 主持人播报题目 →
大屏与手机同步出题并倒计时 → 宾客作答 → 实时计分 → 大屏排行榜。共 13 题。

**三端**

| 端 | 路由 | 使用者 |
|----|------|--------|
| 手机端 | `/` | 宾客（二维码指向此地址） |
| 大屏端 | `/screen?key=<口令>` | 婚礼大屏，1920×1080 横屏 |
| 主持人端 | `/host?key=<口令>` | 主持人手机 / 平板 |

**运行形态**：国内云服务器 2C2G，单进程、单端口（高位端口如 8080），
`http` 明文 + `ws://`，不备案、无域名、无 HTTPS。

## 2. 技术硬约束

| ID | 约束 |
|----|------|
| C1 | 服务端监听**高位端口**，不得用 80/443（未备案的 80 端口被云厂商拦截） |
| C2 | 页面运行在 http 明文下，**禁止依赖任何需要 HTTPS 安全上下文的浏览器能力**（摄像头、剪贴板 API、Service Worker、Web Push、地理位置） |
| C3 | WebSocket 使用 `ws://`，与 HTTP **同端口**（同进程协议升级） |
| C4 | 微信内打开会出现「非微信官方网页」提示条，属预期行为，页面与现场话术均须承接 |
| C5 | 服务器只开放 8080 一个端口（安全组与 `ufw` **两处都要放行**） |
| C6 | **依赖极简**，见 §2.1 |
| **C7** | **仓库为 public**（https://github.com/QiuXin-Mking/wedding-games）。`questions/private.json`（新人隐私题目）与 `data/`（含宾客昵称与成绩的事件日志）**一旦误提交即等于公开发布，缓存与索引无法撤回**。二者必须始终在 `.gitignore` 中，每次提交前须查 `git status` |

### 2.1 C6 依赖预算

| 层 | 允许 | 禁止 |
|----|------|------|
| 运行时依赖 | **最多 1 个**：`ws` | Express / Koa / Fastify / NestJS / Socket.IO |
| 前端 | 零框架、零构建，原生 HTML + CSS + ES Module | React / Vue / Svelte / Vite / webpack / Tailwind / UI 组件库 |
| 语言 | 纯 JavaScript，类型用 JSDoc | TypeScript（引入构建步骤） |
| 测试 | Node 内置 `node:test` | Jest / Vitest / Mocha |
| 数据 | 无数据库：内存 + JSONL 事件日志 | MySQL / PostgreSQL / SQLite / Redis / ORM |
| 二维码 | 离线一次性生成 PNG，产物入库 | 运行时二维码库 |
| CSV 导出 | 手写字符串拼接 | csv 库 |
| 部署 | `node server.js` + systemd unit | Docker / Nginx / PM2 |

**C6.1** HTTP 静态托管用 Node 内置 `http` 手写。
**C6.2** 三个页面各自独立 `.html`，`<script type="module">` 直接引入，无构建产物。
**C6.3** `npm install` 后 `node_modules` 顶层只有 `ws`。
**C6.4** 新增任何依赖前，必须先确认无法用标准库在 100 行内解决。

## 3. 昵称规范（已定稿）

宾客**不可自填昵称**，由服务端从一个 **400 条人工定稿的常量池**按序发放。
发放顺序在生成期定死，**运行时零随机**：第 N 位入场的宾客拿第 N 条。

**结构**：每条昵称 = `前缀词`(2~4 字，含「的」，可复用) + `核心词`(2~3 字，全池唯一)。

### 3.1 七条硬约束

| ID | 约束 | 当前池实测 |
|----|------|-----------|
| U1 | 400 条整条两两不同 | ✅ |
| **U2** | **核心词末二字两两不同**（零复用） | ✅ 0 重复 |
| **U3** | **同一首字的条目 ≤ 12 条** | ✅ 最多 6 条，212 个不同首字 |
| U4 | 长度统一 **4~6 汉字**，纯汉字（无英文 / 数字 / 符号 / 表情） | ✅ 5 字 211 / 6 字 189 |
| **U5** | **禁用词零命中**（见 §3.2） | ✅ 0 命中 |
| U6 | 核心词不得同音；**且须排除与池外常见词的歧义** | ✅ |
| U7 | **核心词必须具象**：判定法是「能不能画出来」 | ✅ |

**U7 判定**：`柯基`、`汤圆`、`灯笼`、`月牙` 能画 → 合格；
`立春`（时间概念）、`好运`（抽象祝愿）、`晴天`（天气状态）画不出来 → 不合格。

**末字封顶**：同一**末字**不超过 4 条。用于治理 U2/U6 抓不到的「听感同质」
（如 `星光/月光/极光/阳光/晨光` 末二字均不同也不同音，但听起来是一串）。

### 3.2 U5 禁用词表

判定标准：**这话能不能当众对一位 56 岁的长辈说。**

| 类别 | 禁用 |
|------|------|
| 食量身材 | 吃、馋、贪、胖、肥、圆滚、肉、膘、口福、肚皮 |
| 懒惰迟钝 | 懒、赖床、睡、打盹、发呆、呆、慢、拖、笨、迟 |
| 外貌年龄 | 丑、秃、矮、短、老、皱 |
| 排序羞辱 | 最后、倒数、垫底 |
| 婚礼忌讳 | 吃席、白、孝、离、散、分、单、空、断、落、梨（谐音「离」）、破、龟、驴 |

**豁免机制**：禁用词按**语义**判定。动物学名中的字若不构成对人的评价，
可逐条进白名单并写明理由。当前白名单仅 `老虎`（「老」是虎的固定名，无年龄义）。

### 3.3 分配与展示

- 服务端维护一个整数游标，宾客首次连接即分配 `池[cursor]` 并 `cursor += 1`。
- 入场页**无任何输入框**，只有一个「进入」按钮。
- 游标与已分配昵称写入事件日志；崩溃重放后完整恢复，**不得把同一昵称分给第二个人**。
- 超过 400 人触发兜底命名（`池[cursor % 400] + 空格 + 序号`）并告警，不崩溃。
- 手机端**所有状态下顶部常驻显示自己的昵称**，不得截断，字号不小于题干。
- 主持人可对指定宾客「发放下一个昵称」，**不可自定义输入**（不得成为绕过机制的后门）。

### 3.4 产物

| 文件 | 说明 |
|------|------|
| `nicknames.json` | 400 条，数组顺序即发放顺序 |
| `昵称池-待审核.md` | 带编号审核清单 |
| `wip/core-*.json` | 545 条候选，替换时从中取备选 |
| `tools/check-nicknames.js` | U1~U6 机器校验，**不通过禁止入库**；服务端启动时复用同一套逻辑 |

## 4. 游戏规则

### 4.1 题库

- 固定 13 题，JSON 配置，字段：题号、题干、选项数组、正确选项下标。**纯文字，无图片**。
- 统一为单选；判断题用 2 个选项「对 / 错」表达。
- 选项顺序**不随机打乱**，保证主持人口播的 A/B/C/D 与两端一致。
- **双题库**：`questions/test.json`（随仓库提交，**默认加载**）与
  `questions/private.json`（**`.gitignore` 排除**，部署时单独投放）。
- 切换由环境变量 `QUIZ_BANK=test|private` 决定，不改代码、不重新构建。
- 指定 `private` 而文件缺失时，**启动失败并报明确错误，绝不静默回退**。
- 启动即校验：题数 = 13、每题选项 ≥ 2、正确下标合法、题干与选项非空，任一不满足即启动失败。
- 大屏与主持人控制台须显示当前题库角标（`测试题库` / `正式题库`）。

### 4.2 计分

```
答对：gained = 100 + floor(max(remainMs, 0) / 1000) × 10
答错：0（不扣分）
超时：0（数据中区分 timeout / wrong / skipped）
remainMs = 服务端截止时间戳 − 服务端收到答案的时刻
```

- 单题最高 250 分，13 题理论满分 3250 分。
- 得分**只在服务端计算**，不采信客户端上报的任何时间戳。
- 排行榜：总分降序 → 答对题累计耗时升序 → 入场序号升序。名次唯一，不出现并列。
- `skipped` 的题不计入累计耗时。

### 4.3 倒计时

- 每题 15 秒，倒计时为**页面中央主视觉元素**（大屏与手机端均是）。
- 服务端倒计时基于**单调时钟**推进，NTP 校时跳变不得导致错乱。
- 客户端连接后与服务端对时（5 次探针取最小 RTT 样本），用时钟偏移换算本地截止时刻，
  倒计时本地推进，**不逐秒依赖网络**。对时全失败时 `offset = 0` 降级。

### 4.4 状态机与主持人动作

```
IDLE --host:start--> READY --host:next--> ASKING --(超时/全员已答)--> REVEAL
                                            ↕ pause/resume          ↓ next
                                          PAUSED                  ASKING(下一题)
                                                      host:finish --> FINAL
```

| 动作 | 合法前置态 | 计分语义 |
|------|-----------|---------|
| `host:next` | READY / REVEAL | 开下一题，`deadlineAt = now() + 15000` |
| `host:extend` | ASKING | `deadlineAt += 10000` 并重播；已提交者不受影响、不可改答案 |
| `host:skip` | ASKING / REVEAL | 全员记 `skipped`、0 分、**不计入累计耗时** |
| `host:back` | REVEAL | **清零该题全员得分与作答**，写 `question_rollback` 事件，重开该题 |
| `host:republish` | REVEAL | 仅重播结算画面，**不触碰任何分数** |
| `host:pause` / `resume` | ASKING / PAUSED | 冻结与恢复剩余毫秒；暂停期间提交一律拒绝 |
| `host:finish` | 任意 | → FINAL，拒绝新入场 |
| `host:nextNickname` | 任意 | 给指定宾客发放 `池[cursor]`，`cursor++` |
| `host:remove` | 任意 | 移除宾客及其成绩 |

## 5. 必须修复的缺陷

以下 10 项已确认为设计缺陷，实现时必须解决。

| # | 缺陷 | 要求 |
|---|------|------|
| 1 | **延长 10 秒导致「越慢分越高」**：原截止前 2 秒提交得 120，延长后第 1 秒提交得 190 | 延长后不得使晚答者获得更高分 |
| 2 | **提前结算的分母是「在线人数」**：掉线 / 息屏者被当作不存在，题目以远快于 15 秒的速度飞过 | 提前结算的判定不得只看在线数；须定义息屏 / 切后台是否算在线 |
| 3 | **`answer` 无服务端回执**：弱网下页面显示「已提交」而结算 0 分 | 只有服务端确认收到，前端才可显示「已提交」 |
| 4 | **`host:extend` 重播 `question` 会冲掉「已提交」态**：载荷无「我已提交」字段，前端整体重写 DOM | `question` 载荷须携带该宾客的提交状态 |
| 5 | **`host:next` 无幂等**：重复点击或多设备同时点击会连跳题 | 动作须带题号并去重 |
| 6 | **`host:back` 天生无效**：唯一合法时机（结算态）恰是答案已公布之时，重答变成集体送分 | 重答须换备用题，或改为「本题作废」 |
| 7 | **协议无面向宾客的公告消息**：extend / skip / back 在宾客端全是无解释突变 | 增加 `notice` 消息类型，每个救场动作都要有宾客可读的说明 |
| 8 | **主持人端无连接状态**：分不清「自己掉线」与「服务器挂了」，而两者处置相反 | 控制台须显示连接状态，并能区分二者；每次点击须有明确回执 |
| 9 | 按钮文案「回到上一题」与实际行为「重开该题」不符 | 按钮文案、主持人口播、宾客屏幕须为同一件事 |
| 10 | 念题时间与倒计时的关系未定义 | 须明确主持人念题期间是否计时 |

## 6. 必须补齐的功能

| # | 功能 | 理由 |
|---|------|------|
| 1 | **主持人控制台显示题干、选项、正确答案** | 主持人需播报题目，但他侧对大屏且灯光晃眼，只能靠背 |
| 2 | **纸质题卡（含答案）** | 「服务器挂了转口头抢答」的应急预案否则无法执行——题目在服务器上 |
| 3 | **「提前结算本题」按钮** | 有人挂机不答时，自动结算触发不了，只能干等 15 秒；而「跳过」会清零全员 |
| 4 | **中途离席再回来的处理** | 敬酒是每桌必然事件，整桌消失 3 分钟即全桌 0 分，构成系统性不公平 |
| 5 | **应急预案话术卡** | 每种故障须配一句可直接照念的话 |
| 6 | **控制台时间预算**（已用时长 / 剩余题数 / 超时提醒） | 现场总时长有限，主持人无从判断进度 |
| 7 | **大屏二维码可随时召回** | 二维码仅在待机态显示，游戏开始后迟到者无法扫码 |
| 8 | **向宾客说明计分规则** | 宾客无从得知「越快分越高」，只能靠邻座倒推 |
| 9 | **手机端字号 / 触控规范** | 全部验收标准中此前无一条涉及手机可读性 |
| 10 | **首屏加载态** | 白屏时长辈会以为没扫上，反复重扫 |
| 11 | **退出后的回归指引** | 长辈不懂「网页」「刷新」，退出微信后找不回游戏 |
| 12 | **可执行的降级预案** | 需指派记分员、准备纸笔、明确「等多久才宣布降级」 |

## 7. 验收标准

### 7.1 同步与计分

| ID | 标准 |
|----|------|
| AC-01 | 扫码打开页面，**页面无输入框**，点「进入」即获得中文昵称并进入等待页，大屏入场人数 +1 |
| AC-02 | 主持人点「下一题」后，大屏与手机显示同一题号与题干；两端渲染完成时间戳差 ≤ 1 秒 |
| AC-03 | 大屏与手机中央均显示 15 秒倒计时，两端读数差 ≤ 1 秒 |
| AC-04 | 提交后选项锁定，重复提交无效，得分与 §4.2 公式一致 |
| AC-05 | 倒计时归零后提交的答案不计分，记为 `timeout` |
| AC-06 | 每题结束大屏显示正确答案、作答分布与 Top 5；13 题结束显示 Top 10 |
| AC-07 | 关闭手机浏览器再打开，昵称与累计得分完整恢复，排名不变 |
| AC-08 | 第 5 题时新入场的宾客能参与第 6 题，前 5 题记 0 分且出现在排行榜中 |
| AC-09 | kill 服务端进程并重启后，所有宾客与得分完整恢复，主持人可从中断题继续 |
| AC-10 | 100 及 400 个模拟客户端并发连接并在同一题内全部提交，不丢答案、不错分，广播延迟 < 1 秒 |
| AC-11 | `/screen` 与 `/host` 在口令错误时无法进入 |
| AC-12 | 主持人可成功执行延长 10 秒 / 跳过 / 回到上一题 / 重新公布 / 暂停继续，计分结果与 §4.4 表格一致；其中**重新公布前后任何人分数不变** |
| AC-13 | 两台设备同时打开主持人端，任一台操作对全场生效，另一台状态同步 |
| AC-14 | 答题中把服务器系统时间人为前后各跳 30 秒，倒计时不错乱 |

### 7.2 题库

| ID | 标准 |
|----|------|
| AC-15 | 不设任何环境变量直接启动，加载**测试题库**，大屏角标显示「测试题库」 |
| AC-16 | `QUIZ_BANK=private` 且文件存在时加载隐私题库，角标显示「正式题库」；**文件缺失时进程启动失败并报明确错误，不回退** |
| AC-17 | 题库故意改错（题数 ≠ 13 / 正确下标越界 / 题干为空）时，服务端启动即失败并指出具体问题 |
| AC-18 | `git status` 中 `questions/private.json` 与 `data/` 均不出现在待提交列表；**远端仓库文件树中同样不存在**（仓库 public，这是唯一防线，见 C7） |

### 7.3 昵称

| ID | 标准 |
|----|------|
| AC-19 | 校验脚本对 `nicknames.json` 执行 U1~U6 **全部通过** |
| AC-20 | 塞入一条违规数据（同尾词 / 7 字 / 含禁用字），脚本**必须报错并指出具体条目**，且服务端启动失败 |
| AC-21 | 400 条已由用户逐条过目确认 |
| AC-22 | 400 条已由**一位 50 岁以上的人独立过目**（无人从旁解释），其指出的条目已替换 |
| AC-23 | U7 抽查：任取 30 个核心词，均可描述为「一个看得见的东西」 |
| AC-24 | 模拟 400 位宾客依次入场，昵称与池文件第 1~400 条**逐一对应、顺序一致**、全部互不重复 |
| AC-25 | 相同入场顺序重跑两次，分配结果**完全一致** |
| AC-26 | 第 401 位宾客入场触发兜底命名并告警，不崩溃 |
| AC-27 | **听辨验收**：任取 10 对昵称，在**背景噪音环境下隔 5 米朗读**，听者能正确区分 |
| AC-28 | **远距离验收**：大屏 Top 10 投到实际尺寸，**从宴会厅最后一排（12~15 米）**能逐条读出 |
| AC-29 | 手机端五个状态下顶部均常驻显示昵称，**不被截断，字号不小于题干** |

## 8. 明确不做

- 微信 OAuth 登录、获取微信头像昵称
- 宾客聊天、弹幕、红包、抽奖转盘
- 图片题、音频题、视频题
- 题库在线编辑后台；运行时热切换题库（切换需重启）
- 多场婚礼 / 多房间 / 多租户
- 用户账号体系、后台管理系统
- 国际化（仅中文）
- HTTPS、域名、ICP 备案
- 历史场次数据统计与分析
- 前端构建流水线、TypeScript、组件库、CSS 框架
- 容器化、反向代理、进程管理器
- 宾客自定义昵称；机器造词
- 按昵称推断真实身份的映射表

## 9. 已接受的风险

| 风险 | 决策 |
|------|------|
| 单点故障：全场依赖一台服务器一个进程，云厂商抖动无技术兜底 | 接受。降级为口头抢答 |
| 宾客清缓存 / 换设备后身份与分数不可找回 | 接受。不做找回 |
| 大屏 URL 含口令，全屏失败时会投影给全场 | 接受。`/screen` 只读，危害有限 |
| 宾客开多个无痕窗口可注册多个身份刷分 | 接受。不做设备指纹 |
| 同桌之间互相看屏幕抄答案 | 接受 |
| 现场人数超过 400 触发兜底命名 | 接受。已确认不超过 400 人 |

**总定调**：**计分若在现场失效，游戏降级为纯粹的气氛活动** —— 主持人照常播报、
大屏照常出题，不追求分数正确性，不中断婚礼流程。
因此韧性做到「不卡死」即可，不必为「绝对不丢分」过度设计；
但「打不开」与「卡死」没有降级空间，相关要求不可削减。
