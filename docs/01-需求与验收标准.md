# 01 · 需求与验收标准

> 婚礼互动答题小游戏 H5 ｜ 婚礼日期 2026-10-06
> 本文件自包含：**只写最终结论与可检验的标准**，不含推导过程。

## 1. 产品定义

婚礼现场「大屏 + 宾客手机」实时答题：宾客扫码入场 → 系统分配昵称 → 主持人播报题目 →
大屏与手机同步出题并倒计时 → 宾客作答 → 实时计分 → 大屏排行榜。共 13 题。

**三端**

| 端 | 路由 | 使用者 |
|----|------|--------|
| 手机端 | `/` | 宾客（二维码指向此地址） |
| 大屏端 | `/screen?key=<口令>` | 婚礼大屏，1920×1080 横屏 |
| 主持人端 | `/host?key=<口令>` | 主持人手机 / 平板 |

**传输协议**：WebSocket（`ws://`，与 HTTP 同端口）。选型论证见 §2.3。

**运行形态**：腾讯云 **OpenCloudOS 9.6**（RHEL 系，包管理 `dnf`），2 核 2G，37G 可用磁盘。
公网 `119.29.186.63`，SSH 免密（root）。单进程、单端口 **8888**，`http` 明文 + `ws://`，
不备案、无域名、无 HTTPS。本机实测 RTT **平均 12ms**（最低 7ms），TCP 握手 3~24ms。
**SELinux 已禁用、firewalld 未启用**，仅云安全组生效；**8888 已用真实 HTTP 响应验证放行**
（以未放行的 9999 作对照组）。

## 2. 技术硬约束

| ID | 约束 |
|----|------|
| C1 | 服务端监听高位端口 **8888**，不得用 80/443（未备案的 80 端口被云厂商拦截）。8888 是常见的 HTTP 备用端口 |
| C2 | 页面运行在 http 明文下，**禁止依赖任何需要 HTTPS 安全上下文的浏览器能力**（摄像头、剪贴板 API、Service Worker、Web Push、地理位置） |
| C3 | WebSocket 使用 `ws://`，与 HTTP **同端口**（同进程协议升级） |
| C4 | 微信内打开会出现「非微信官方网页」提示条，属预期行为，页面与现场话术均须承接 |
| C5 | 服务器只开放 **8888** 一个端口。实测 firewalld 未启用、SELinux 已禁用，**只需云安全组**（已放行）。若后续启用 firewalld，须同步放行 |
| C6 | **依赖极简**，见 §2.1 |
| **C7** | **仓库为 public**（https://github.com/QiuXin-Mking/wedding-games）。新人的题目属新人自己的信息，已决定**随仓库公开提交**；但 `data/`（事件日志，含 400 位宾客的昵称与成绩）是**他人的数据、未经其同意**，必须始终在 `.gitignore` 中，绝不入库 |

### 2.3 带宽预算（**3 Mbps = 366 KB/s**，用户提供）

#### 传输协议选型（决策 D13）

| 方案 | 持续带宽占用 | 满足 AC-02（1 秒内同步）？ |
|------|-------------|--------------------------|
| HTTP 轮询 500ms | 800 req/s × 350B = **2.24 Mbps，占 75%** | ✅ 但与首屏加载抢带宽 |
| HTTP 轮询 1s | 400 req/s × 350B = **1.12 Mbps，占 37%** | ⚠️ 最坏 1s + RTT，**踩线** |
| **WebSocket** | 单次广播 400×250B = 100 KB，**0.27 秒发完**；持续 ≈ **1%** | ✅ 有余量 |

**结论：采用 WebSocket。** 理由不是「实时游戏惯例」，而是 3 Mbps 这个具体数字把轮询挤掉了 ——
轮询要么吃掉四分之三带宽，要么延迟正好卡在验收线上。
全场 13 题总推送量约 3.6 MB，摊在 15 分钟里平均 4 KB/s。

> 轮询本可以消灭一整类问题（无连接态、无重连、无退避，且「在线人数」这个
> 会导致提前结算出错的概念根本不存在）。是带宽否决了它，不是它不好。
> 因此 WebSocket 方案**必须额外处理**这些连接态问题（见 §5 缺陷 2/3/4/7/8）。


#### 为什么是 WebSocket 而不是裸 TCP

**WebSocket 本身就是 TCP 长连接** —— TCP 之上一层很薄的分帧，经一次 HTTP Upgrade 建立。

| 项 | 开销 |
|----|------|
| 帧头 | **2 字节**（服务端→客户端）/ 6 字节（客户端→服务端，含掩码） |
| 250 字节消息 | **0.8% ~ 2.4%** |
| 握手 | 每客户端一次约 400 字节 |

裸 TCP 省不下来 —— 自己做分帧同样要 2~4 字节长度前缀。
且有一条决定性事实：**浏览器没有裸 TCP 的 API**，H5 只能用
HTTP / WebSocket / WebRTC / WebTransport。WebRTC DataChannel 需要
STUN/TURN + 信令 + DTLS，复杂度爆炸且违反 C6。

**协议不是字节大头，首屏静态资源才是。**

#### 入场峰值：集中扫码（已确认为真·峰值）

主持人喊完口令后 400 人几秒内同时扫码，**不可能提前打散**。TCP 公平分配下每人约 900 B/s。

| 项 | 量 |
|----|----|
| 400 × 单文件 HTML（10 KB gzip） | 4.0 MB |
| 400 × WebSocket 握手 | 0.16 MB |
| 400 × 首次 `snapshot` | 0.2 MB |
| **合计 ÷ 366 KB/s** | **≈ 12 秒** |

注意这是「**所有人一起等 12 秒**」，不是有快有慢 —— 公平分配下大家同时完成。

**对策（全部为强制要求）**：

| ID | 要求 | 效果 |
|----|------|------|
| **P-1** | **单文件内联**：HTML + CSS + JS 全部内联进一个 `.html`，**只发 1 个请求** | 省字节，更省 400×4=1600 次请求往返 |
| **P-2** | **首屏 ≤ 10 KB（gzip 后）**，见 AC-31 | 线性决定峰值时长 |
| **P-3** | **HTML 前 600 字节内必须含 `<style>` 与一句可见文字** | 浏览器流式渲染，**1 秒出「正在进入」**，12 秒完全可交互 |
| **P-4** | **内联 data URI favicon** | 否则浏览器自动多发 400 次 `/favicon.ico` |
| **P-5** | **静态资源预压缩**为 `.gz` 落盘，不做运行时压缩 | 省 CPU，峰值期 CPU 要留给 WS |
| **P-6** | `Cache-Control: max-age=3600` | 刷新与重连不重复下载 |
| **P-7** | **昵称池与题库一律不下发客户端** | 昵称池 400 条无必要；题库含答案，下发即作弊 |

> P-3 同时治掉演练问题 A-04 / B-04：白屏让宾客以为没扫上而反复重扫，
> 而重扫会让本已紧张的带宽进一步恶化 —— 这是会自我放大的故障。

#### 连接层限制（实测并已修复 2026-09-22）

```
somaxconn 4096 ✅    tcp_max_syn_backlog 2048 ✅    tcp_syncookies 1 ✅    内核 6.6 ✅
```

**fd 上限（已查清并修复）**：

| 路径 | 修复前 | 修复后 |
|------|-------|-------|
| systemd 服务 | **524288**（发行版默认，本就够用） | 不变；unit 仍显式写死不依赖默认 |
| SSH 交互式 shell | **1024** | **65535**（已写 `/etc/security/limits.d/99-wedding-quiz.conf`，新会话已验证） |

> 交互式 shell 那条路径是真会中招的场景：**婚礼当天有人 SSH 上去手动 `node server.js`**
> 排查或重启，继承的就是 1024。应急预案里正有这一步。

| ID | 要求 |
|----|------|
| **P-8** | systemd unit 显式设 `LimitNOFILE=65535`，不依赖发行版默认 |
| **P-9** | Node `server.listen()` 显式指定 backlog ≥ 1024（默认 511，低于内核 4096） |

#### 入场等待的交互设计（P-10 ~ P-13）

峰值期全场需等约 12 秒。**转圈动画不传达进度，只传达「还在等」**，12 秒的 spinner
与卡死无异。以下为强制要求：

| ID | 要求 | 说明 |
|----|------|------|
| **P-10** | **真实进度条**：在 HTML 文件每约 20% 处埋一个内联 `<script>` 上报进度 | 浏览器流式解析到哪就报到哪，**是真进度不是假动画**。成本约 200 字节。**禁止假进度条** —— 卡在 90% 比白屏更令人烦躁 |
| **P-11** | **分阶段文案**：`正在进入…` → `正在为你取名字…` → **昵称揭晓** | 让 12 秒有推进感 |
| **P-12** | **昵称揭晓做成一次小小的揭晓动画** | 把等待变成期待：12 秒的尽头有个属于自己的东西被揭晓。同时强化记忆（演练 A-03：宾客三秒就忘了自己的昵称） |
| **P-13** | 动画**纯 CSS、无图片**，且**只动 `transform` / `opacity`** | 图片会产生额外请求（违反 P-1/P-4）；进度条须用 `scaleX()` 而非 `width` —— 400 台老手机同时跑动画，动布局属性会掉帧 |

#### 入场首屏（历史估算，已被上方峰值预算取代）

```
400 人 × 首屏大小 ÷ 366 KB/s
  100 KB → 109 秒      30 KB → 33 秒      20 KB → 22 秒
```

**若主持人喊「大家现在一起扫码」，最后一位宾客会白屏近两分钟。** 两条对策：

1. **首屏压到 30 KB 以内**（AC-31）。零框架下现实可达；若用 React 则首屏 150 KB+，
   400 人需 164 秒 —— C6 这条约束当初是为了少出错，实际也是带宽的救命稻草。
2. **话术禁止集中扫码**：桌卡在宾客入座时就已摆好，让其陆续扫入。
   主持人**不得**喊「现在大家一起扫」（写入 FR-9.4 操作手册）。

## 3. 昵称规范（已定稿）

宾客**不可自填昵称**，由服务端从一个 **400 条人工定稿的常量池**按序发放。
发放顺序在生成期定死，**运行时零随机**：第 N 位入场的宾客拿第 N 条。

**结构**：每条昵称 = `前缀词`(2~4 字，含「的」，可复用) + `核心词`(2~3 字，全池唯一)。

### 3.1 七条硬约束

| ID | 约束 | 当前池实测 |
|----|------|-----------|
| U1 | 400 条整条两两不同 | ✅ |
| **U2** | **核心词末二字两两不同**（零复用） | ✅ 0 重复 |
| **U3** | **同一首字的条目 ≤ 12 条** | ✅ 最多 6 条，212 个不同首字 |
| U4 | 长度统一 **4~6 汉字**，纯汉字（无英文 / 数字 / 符号 / 表情） | ✅ 5 字 211 / 6 字 189 |
| **U5** | **禁用词零命中**（见 §3.2） | ✅ 0 命中 |
| U6 | 核心词不得同音；**且须排除与池外常见词的歧义** | ✅ |
| U7 | **核心词必须具象**：判定法是「能不能画出来」 | ✅ |

**U7 判定**：`柯基`、`汤圆`、`灯笼`、`月牙` 能画 → 合格；
`立春`（时间概念）、`好运`（抽象祝愿）、`晴天`（天气状态）画不出来 → 不合格。

**末字封顶**：同一**末字**不超过 4 条。用于治理 U2/U6 抓不到的「听感同质」
（如 `星光/月光/极光/阳光/晨光` 末二字均不同也不同音，但听起来是一串）。

### 3.2 U5 禁用词表

判定标准：**这话能不能当众对一位 56 岁的长辈说。**

| 类别 | 禁用 |
|------|------|
| 食量身材 | 吃、馋、贪、胖、肥、圆滚、肉、膘、口福、肚皮 |
| 懒惰迟钝 | 懒、赖床、睡、打盹、发呆、呆、慢、拖、笨、迟 |
| 外貌年龄 | 丑、秃、矮、短、老、皱 |
| 排序羞辱 | 最后、倒数、垫底 |
| 婚礼忌讳 | 吃席、白、孝、离、散、分、单、空、断、落、梨（谐音「离」）、破、龟、驴 |

**豁免机制**：禁用词按**语义**判定。动物学名中的字若不构成对人的评价，
可逐条进白名单并写明理由。当前白名单仅 `老虎`（「老」是虎的固定名，无年龄义）。

### 3.3 分配与展示

- 服务端维护一个整数游标，宾客首次连接即分配 `池[cursor]` 并 `cursor += 1`。
- 入场页**无任何输入框**，只有一个「进入」按钮。
- 游标与已分配昵称写入事件日志；崩溃重放后完整恢复，**不得把同一昵称分给第二个人**。
- 超过 400 人触发兜底命名（`池[cursor % 400] + 空格 + 序号`）并告警，不崩溃。
- 手机端**所有状态下顶部常驻显示自己的昵称**，不得截断，字号不小于题干。
- 主持人可对指定宾客「发放下一个昵称」，**不可自定义输入**（不得成为绕过机制的后门）。

| 文件 | 说明 |
|------|------|
| `nicknames.json` | 400 条，数组顺序即发放顺序 |
| `昵称池-待审核.md` | 带编号审核清单 |
| `wip/core-*.json` | 545 条候选，替换时从中取备选 |

## 4. 游戏规则

### 4.1 题库

- **13 道正题 + 3 道备用题**，JSON 配置，字段：题号、题干、选项数组、正确选项下标、`spare`(bool)。**纯文字，无图片**。
  备用题供 `host:back` 换题使用（§4.4），不参与正常出题顺序。
- 统一为单选；判断题用 2 个选项「对 / 错」表达。
- 选项顺序**不随机打乱**，保证主持人口播的 A/B/C/D 与两端一致。
- **双题库**：`questions/test.json`（**默认加载**）与 `questions/wedding.json`（真实婚礼题）。
  **两者均随仓库提交**（C7：仓库公开，新人题目已决定公开）。
- 切换由环境变量 `QUIZ_BANK=test|wedding` 决定，不改代码、不重新构建。
- 指定 `wedding` 而文件缺失时，**启动失败并报明确错误，绝不静默回退**。
- 启动即校验：**正题 = 13 道、备用题 ≥ 1 道**、每题选项 ≥ 2、正确下标合法、题干与选项非空，
  任一不满足即启动失败。
- 大屏与主持人控制台须显示当前题库角标（`测试题库` / `正式题库`）。

### 4.2 计分

```
答对：gained = 100 + floor(max(remainMs, 0) / 1000) × 10
答错：0（不扣分）
超时：0（数据中区分 timeout / wrong / skipped）
remainMs = 服务端截止时间戳 − 服务端收到答案的时刻
```

- 单题最高 **300** 分（20 秒题即答即对），13 题理论满分 **3900** 分。
- 得分**只在服务端计算**，不采信客户端上报的任何时间戳。
- **倒计时结束前允许改答案**，按**最后一次**提交计分：`remainMs` 取最后一次提交到达服务端的时刻。
  改答案会因剩余时间变少而掉分，这是预期行为。事件日志记录每一次提交，重放时取最后一条。
- 排行榜：总分降序 → 答对题累计耗时升序 → 入场序号升序。名次唯一，不出现并列。
- `skipped` 的题不计入累计耗时。

### 4.3 倒计时

- 每题 **20 秒**，倒计时为**页面中央主视觉元素**（大屏与手机端均是）。
- **主持人先念完题、再点「下一题」**；点下的瞬间开始计时，念题时间不占用答题时间。
  状态机不设「预备态」。
- 服务端倒计时基于**单调时钟**推进，NTP 校时跳变不得导致错乱。
- 客户端连接后与服务端对时（5 次探针取最小 RTT 样本），用时钟偏移换算本地截止时刻，
  倒计时本地推进，**不逐秒依赖网络**。对时全失败时 `offset = 0` 降级。

### 4.4 状态机与主持人动作

```
IDLE --host:start--> READY --host:next--> ASKING --(超时/全员已答/手动结算)--> REVEAL
                                            ↕ pause/resume          ↓ next
                                          PAUSED                  ASKING(下一题)
                                                      host:finish --> FINAL
```

| 动作 | 合法前置态 | 计分语义 |
|------|-----------|---------|
| `host:next` | READY / REVEAL | 开下一题，`deadlineAt = now() + 20000`。**动作须带当前题号，服务端去重**（同一题只可能前进一次） |
| `host:extend` | ASKING | `deadlineAt += 10000` 并重播。**计分仍按原截止时刻** —— 延长期间提交的答案 `remainMs ≤ 0`，**一律 0 分**。延长只给「看清题」的机会，不补分 |
| `host:earlySettle` | ASKING | **立即结算本题**，未提交者记 `timeout`、0 分。用于有人挂机时不干等 |
| `host:skip` | ASKING / REVEAL | 全员记 `skipped`、0 分、**不计入累计耗时**。大屏显示「本题作废」，**不公布答案** |
| `host:back` | REVEAL | **换一道备用题**重开（原题作废、全员记 `skipped`、0 分）。不重答已公布答案的原题 |
| `host:republish` | REVEAL | 仅重播结算画面，**不触碰任何分数** |
| `host:pause` / `resume` | ASKING / PAUSED | 冻结与恢复剩余毫秒；暂停期间提交一律拒绝 |
| `host:finish` | 任意 | → FINAL，拒绝新入场 |
| `host:nextNickname` | 任意 | 给指定宾客发放 `池[cursor]`，`cursor++` |
| `host:remove` | 任意 | 移除宾客及其成绩 |

## 5. 必须修复的缺陷

以下 10 项已确认为设计缺陷，实现时必须解决。

| # | 缺陷 | 要求 |
|---|------|------|
| 1 | **延长 10 秒导致「越慢分越高」**：原截止前 2 秒提交得 120，延长后第 1 秒提交得 190 | 延长后不得使晚答者获得更高分 |
| 2 | **提前结算的分母是「在线人数」**：掉线 / 息屏者被当作不存在，题目以远快于 15 秒的速度飞过 | 提前结算的判定不得只看在线数；须定义息屏 / 切后台是否算在线 |
| 3 | **`answer` 无服务端回执**：弱网下页面显示「已提交」而结算 0 分 | 只有服务端确认收到，前端才可显示「已提交」 |
| 4 | **`host:extend` 重播 `question` 会冲掉「已提交」态**：载荷无「我已提交」字段，前端整体重写 DOM | `question` 载荷须携带该宾客的提交状态 |
| 5 | **`host:next` 无幂等**：重复点击或多设备同时点击会连跳题 | 动作须带题号并去重 |
| 6 | **`host:back` 天生无效**：唯一合法时机（结算态）恰是答案已公布之时，重答变成集体送分 | 重答须换备用题，或改为「本题作废」 |
| 7 | **协议无面向宾客的公告消息**：extend / skip / back 在宾客端全是无解释突变 | 增加 `notice` 消息类型，每个救场动作都要有宾客可读的说明 |
| 8 | **主持人端无连接状态**：分不清「自己掉线」与「服务器挂了」，而两者处置相反 | 控制台须显示连接状态，并能区分二者；每次点击须有明确回执 |
| 9 | 按钮文案「回到上一题」与实际行为「重开该题」不符 | 按钮文案、主持人口播、宾客屏幕须为同一件事 |
| 10 | 念题时间与倒计时的关系未定义 | 须明确主持人念题期间是否计时 |

## 6. 必须补齐的功能

| # | 功能 | 理由 |
|---|------|------|
| 1 | **主持人控制台显示题干、选项、正确答案** | 主持人需播报题目，但他侧对大屏且灯光晃眼，只能靠背 |
| 2 | **纸质题卡（含答案）** | 「服务器挂了转口头抢答」的应急预案否则无法执行——题目在服务器上 |
| 3 | **「提前结算本题」按钮** | 有人挂机不答时，自动结算触发不了，只能干等 15 秒；而「跳过」会清零全员 |
| 4 | **中途离席再回来的处理** | 敬酒是每桌必然事件，整桌消失 3 分钟即全桌 0 分，构成系统性不公平 |
| 5 | **应急预案话术卡** | 每种故障须配一句可直接照念的话 |
| 6 | **控制台时间预算**（已用时长 / 剩余题数 / 超时提醒） | 现场总时长有限，主持人无从判断进度 |
| 7 | **大屏二维码可随时召回** | 二维码仅在待机态显示，游戏开始后迟到者无法扫码 |
| 8 | **向宾客说明计分规则** | 宾客无从得知「越快分越高」，只能靠邻座倒推 |
| 9 | **手机端字号 / 触控规范** | 全部验收标准中此前无一条涉及手机可读性 |
| 10 | **首屏加载态** | 白屏时长辈会以为没扫上，反复重扫 |
| 11 | **退出后的回归指引** | 长辈不懂「网页」「刷新」，退出微信后找不回游戏 |
| 12 | **可执行的降级预案** | 需指派记分员、准备纸笔、明确「等多久才宣布降级」 |

### 7.1 同步与计分

| ID | 标准 |
|----|------|

| AC-05 | 倒计时归零后提交的答案不计分，记为 `timeout` |

| AC-10 | 100 及 400 个模拟客户端并发连接并在同一题内全部提交，不丢答案、不错分，广播延迟 < 1 秒 |
| AC-11 | `/screen` 与 `/host` 在口令错误时无法进入 |

## 8. 明确不做

- 微信 OAuth 登录、获取微信头像昵称
- 宾客聊天、弹幕、红包、抽奖转盘
- 图片题、音频题、视频题
- 题库在线编辑后台；运行时热切换题库（切换需重启）
- 多场婚礼 / 多房间 / 多租户
- 用户账号体系、后台管理系统
- 国际化（仅中文）
- HTTPS、域名、ICP 备案
- 历史场次数据统计与分析
- 前端构建流水线、TypeScript、组件库、CSS 框架
- 容器化、反向代理、进程管理器
- 宾客自定义昵称；机器造词
- 按昵称推断真实身份的映射表

## 9. 已接受的风险

| 风险 | 决策 |
|------|------|
| 单点故障：全场依赖一台服务器一个进程，云厂商抖动无技术兜底 | 接受。降级为口头抢答 |
| 宾客清缓存 / 换设备后身份与分数不可找回 | 接受。不做找回 |
| 大屏 URL 含口令，全屏失败时会投影给全场 | 接受。`/screen` 只读，危害有限 |
| 宾客开多个无痕窗口可注册多个身份刷分 | 接受。不做设备指纹 |
| 同桌之间互相看屏幕抄答案 | 接受 |
| 现场人数超过 400 触发兜底命名 | 接受。已确认不超过 400 人 |

**总定调**：**计分若在现场失效，游戏降级为纯粹的气氛活动** —— 主持人照常播报、
大屏照常出题，不追求分数正确性，不中断婚礼流程。
因此韧性做到「不卡死」即可，不必为「绝对不丢分」过度设计；
但「打不开」与「卡死」没有降级空间，相关要求不可削减。
