# 02 · 宾客端实现要点

> `public/index.html` 里每一处不直观的写法，理由都在这里。
> 代码里用 `/*→D3*/` 这样的锚点指回本文的编号。
>
> **为什么搬出来**：宾客端首屏有一条硬预算 —— gzip ≤ 10 KB（AC-31、P-2），
> 它线性决定 400 人集中扫码要一起等多少秒。注释服务于未来的维护者，
> 那 10 KB 服务于当天在场的每一位宾客。冲突时后者优先，
> 所以解释挪到这里，代码里只留锚点。
>
> 改 `index.html` 前先读这里；改完记得 `npm test`（有一条会盯首屏体积）。

---

## 一、首屏与加载

### D1 · 进度条是真的，不是定时器动画

HTML 文件里每隔约 20% 埋一个内联 `<script>p(n)</script>`，浏览器解析到哪就报到哪。

**不允许改成定时器假进度。** 假进度条卡在 90% 比白屏更折磨人 —— 白屏至少诚实，
假进度会让人反复重扫，而重扫会让本已紧张的带宽进一步恶化，这是会自我放大的故障。

> 对应 P-10

### D2 · 12 秒兜底文案

连不上时不能永远停在「正在进入…」加一条走满的进度条 —— 那正是「假进度卡住」的观感。
12 秒还没进入游戏就说人话，并给一个能点的重试出口。

> 对应 P-11 / AC-39

### D3 · boot 块必须排在所有样式之前

`<div id=boot>` 和它那段内联脚本要先于 `<style>` 到达。浏览器边收边渲染，
400 人集中扫码时每人只分到约 900 B/s，这样才能在 1 秒内先出「正在进入」。

> 对应 P-3

## 二、倒计时

### D4 · 位置：题干正上方，不在角落

演练里宾客的原话是右上角那个小数字「根本不看」，而倒计时是全场唯一的紧迫感来源。
`tabular-nums` 保证位数变化时数字不左右跳。

### D5 · 尺寸：题干的约 1.7 倍，是层级问题不是大小问题

题干（22px）必须是主角，倒计时是给节奏的配角。430px 屏实测 36px。

四档实机比选的结论：

| 尺寸 | 结论 |
|------|------|
| 64px | 数字抢走全部注意力，**正是演练里「要看的题被挤下去」那个状态**，否决 |
| 46px | 可用，但没必要 |
| **36px** | 一眼看得见，但明确是配角。**采用** |
| 28px | 与题干平级，紧迫感消失，等于没改，否决 |

要调就调这个**比例关系**，不是拍一个新数字。改 `#tick` 的 `clamp()` 中间值即可。

> 详见 docs/01 §4.3

### D6 · 最后 5 秒的心跳只动 transform

数字本身任何时刻都是实的。动画没跑起来（后台标签页、降级浏览器）也照样看得见。

> 对应 AC-61，原理见 D8

### D7 · 倒计时与题目必须同属一个居中块

`main` 是垂直居中的。倒计时若钉在 `main` 外面，手机上两者之间会被撑开近 200px 空白，
压迫感全散掉。所以结构是 `main > (#tick + #view)`，不是 `#tick + main`。

## 三、动画与可见性（最重要的一组教训）

### D8 · 内容的可见性绝不能取决于动画是否跑起来

**这一条是踩出来的，代价是三次返工。**

标签页隐藏时，浏览器会把动画冻在 0% 帧，`requestAnimationFrame` 也会被暂停。
宾客锁屏、或切去微信回消息，正好赶上昵称揭晓 —— 靠 JS 加 class 点亮的元素，
或者以 `opacity:0` 起步的元素，就会**永远停在不可见状态**。

任何 `fill-mode` 都救不回来。试过 `both`、试过 `forwards`，都不行。

所以规则是：

- **装饰可以动，正文不能。** 正文的 opacity 恒为 1，只用 `transform` 做入场
- 最坏情况下昵称只是小 6%，照样读得清
- 入场效果用 CSS `animation`，不靠 JS 加 class

适用于：昵称揭晓（D9）、发奖点名全屏（D10）、倒计时心跳（D6）。

> 对应 AC-61

### D9 · 昵称揭晓

用 CSS 入场动画，不靠 JS 点亮，理由见 D8。

### D10 · 发奖点名：被叫到的人全屏亮起

随机昵称切断了名字与真人的联系。演练里三个角色撞上的是同一件事：

- 主持人对着三百人念一个没人应的名字
- 宾客把「开心的柯基」听成「幸运的锦鲤」
- 长辈「不敢举手，怕举错了丢人」

这一层就是让当事人确信「叫的是我」。注意**不以 `opacity:0` 起步**（D8）。

> 对应 Q-N1 / 演练 X-3

## 四、存储与降级

### D11 · localStorage 一律包 try/catch

iOS 无痕模式下 `localStorage` 会抛异常。全部包起来并退化为内存态 ——
**宁可刷新丢身份，也不能白屏**。

## 五、入场

### D12 · 「进入」按钮的救生索

点下即变灰，等服务端发 `identity`。失败路径不止一条：被拒、消息在路上丢了、
服务端压根没回。任何一条走到，按钮都会永远灰着 —— 那位宾客彻底进不去，
还不知道为什么。400 人里碰上几个就是现场事故。

所以**不猜失败原因**，只认一件事：8 秒还没进去，就把按钮还给他。

被拒时也必须真的把按钮放回去 —— 文案写着「再试一次」却点不动，是在骗人。

> 服务端对应的约定：`join` 缺 `clientId` 时回 `badJoin`，绝不静默丢弃

## 六、杂项

### D13 · `stopTick` 用 `className=` 而不是 `classList.add`

`className='idle'` 会一并抹掉 `urge`（心跳类），所以不需要单独清。
**但别把它改成 `classList.add`** —— 那样心跳会留在上面一直跳。

## 七、结算页

### D14 · 结算页必须回答的三件事

演练中三位宾客各自撞上一条，合起来正好是结算页该说而没说的三件事。

**① 正确答案。** 13 道题全是关于新郎新娘的，宾客最想知道的恰恰是答案。
原先只能抬头看大屏 —— 而那一刻他可能正在碰杯、正在跟同桌说话，一错过就永远不知道了。
所以答案必须出现在他自己手机上。

**② 第几题 / 共几题。** 中途离开又回来的人（伴娘、去敬酒的人、被叫走的人）
第一眼想知道的是「我现在在哪」。没有题号，他只能抬头找大屏，
在嘈杂的宴会厅里这很可能失败，于是产生「不知道自己掉了多少队」的心慌。

**③ 最后一题要收尾。** 原先第 13 题结算后，手机上依然写着「下一题马上来」。
但此刻主持人正在唱分、讲话、准备发奖，这段空等可能长达一两分钟 ——
全场三百人会一直以为还有下一题。最后一题必须改口说「全部答完了，看大屏公布最终排名」。

顺带把非最后一题的文案从「下一题马上来」改成「看大屏 · **等主持人出下一题**」：
「马上」是个会落空的承诺，主持人唱完分还要说好一会儿话。

判断最后一题需要总题数，所以 `S` 里存了 `total`（从 `snapshot` 与 `question` 两处都取，
哪个先到用哪个）。
